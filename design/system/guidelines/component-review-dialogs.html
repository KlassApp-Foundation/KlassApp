Dialogs & notifications

Right now four libraries do this job. The main shell loads SweetAlert v1 (swal({...}), used on dozens of admin pages) plus toastr. SiteAdmin loads SweetAlert2 v11 + livewire-alert. The calendar pulls in jquery.toastmessage. The proposal is one native <dialog> and one toast stack in styles/feedback-v2.css, with every action a real .ds-btn from the current system (so no "success" button — it's retired).

Toast vs inline alert vs dialog

UseWhenExample
ToastConfirms something the user just did. Disappears by itself (5s, 8s if it has an action), and the timer pauses on hover or focus. Announced with role="status" (errors use role="alert" and don't auto-close)."Fee reminder sent to 6 parents"
Inline alertA condition that stays true until it's fixed. Stays on the page and is never a toast."SchoolPay isn't connected — payments won't sync"
DialogBlocks until the user decides: destructive or hard-to-reverse actions, or a small focused edit.Delete, promote a class, edit class details

Decisions — resolved 2026-09-27

1 · livewire-alert → replaced (decided). It's used in about 9 SiteAdmin Livewire components (AdminForm, CreateSchool, ChangePassword, SubscriptionForm, CityForm…), always as $this->alert('success'|'error', $message). The replacement is a small trait with the same method signature, so migrating each component is a one-line change of use LivewireAlert; → use DispatchesAlerts;: 
trait DispatchesAlerts {
    protected function alert(string $type, string $message = '', array $options = []): void {
        $this->dispatch('alert', type: $type, message: $message, title: $options['title'] ?? null);
    }
}
That fires the alert window event the main shell already handles (event.detail.type / message / title), so SiteAdmin and the school dashboards end up on one event and one renderer. After that, drop livewire-alert.js and the SweetAlert2 CDN from superadmin-app.blade.php. Toast copy loses "successfully": "School created", "Password changed".
2 · Undo — soft deletes are widespread, but restore isn't. About 70 models use SoftDeletes, including Bulletin (the magazine in the demo above), so most deletes are recoverable in the database. But only one controller exposes a way back: UgSubjectController has an archive list, restore() and forceDelete(). Everything else soft-deletes with no restore route. So Undo is possible, but each resource needs a restore endpoint first. Recommendation: pilot "Undo" on Subjects, where the endpoint already exists, and add it elsewhere resource by resource as restore routes land. Until then the delete toast stays without Undo, and the "This can't be undone" line in the dialog is true from the user's point of view — keep it until the route exists. Not verified: whether every delete path goes through Eloquent (which soft-deletes) or through DB::table() (which doesn't).
3 · Toshi's confirm card stays separate. .toshi-confirm-card is an in-chat approval in the clay palette, part of the assistant's own identity. It isn't a dialog and shouldn't be merged into this one.
