# Marks blueprint vs marks-flow spec

Blueprint: [`marks.json`](marks.json), exported from the n8n workflow "KlassApp Blueprint: Marks" (41 nodes, inactive, read once on 2026-10-26 02:32 EAT).
Spec: [`docs/product/marks-flow.md`](../product/marks-flow.md) in this pull request, starting from the version approved on 2026-10-25 (`main` at `ac36ca66`). Open PR #1234 still edits that file's phase table. Redo this comparison if #1234 merges or the blueprint changes.

The blueprint file is unchanged. This pull request updates the spec for items 1, 10, and 16. Every other numbered difference is a simplification: the blueprint omits detail the spec already covers, and the spec stays as it is.

## What was stripped from the export

`settings.errorWorkflow`, the workflow id, `versionId`, `meta.instanceId` (empty in the export), every node's `webhookId` (5 nodes: the form trigger and four form waits), every `credentials` block (there were none), and pinned data (there was none). Instance-only fields were also left out: sharing scopes, `canExecute`, `activeVersion`, `parentFolderId`, timestamps, and the trigger-info text. Node ids, positions, parameters, connections, settings, and node groups are kept so the file imports cleanly.

The five email addresses all use the reserved `demo.invalid` domain. Parent `phone` is `null`. No phone numbers, URLs, tokens, or keys. Nothing needed replacing.

## Disagreements (blueprint vs spec)

1. **No Meta template-approval gate on the WhatsApp send.** *(spec updated in this PR)* Blueprint: `System: check WhatsApp switch` goes straight to `WhatsApp: send results_released template to approved, linked parents`. Spec: the first flowchart has `Results template approved by Meta` between the switch and the send. Phase 6, the release paragraph, Decision 3, step 6, step 8, and the template section now state that a WhatsApp results send only happens once the template it uses is approved by Meta. With the switch on before approval, the release still opens portal, Toshi and report cards and sends nothing. The blueprint still has no approval gate.
2. **No "release past sittings" action.** *(simplification)* Blueprint releases only the current sitting (`Admin: release sitting`), and nothing shows old sittings staying hidden. Spec: Decision 4, step 6, phase 6 and the `past` node in the flowchart need a separate "release past sittings" action with its own confirmation. The blueprint omits that action. The spec already covers it.
3. **The combined sheet appears only after every subject is approved.** *(simplification)* Blueprint: `System: check all subjects approved` (true) → `Admin and class teacher: view combined mark sheet`. When any subject is not approved, the flow ends at `System: block release until all approved` and staff see no sheet. Spec ("The flow" and step 5): staff can open the sheet and the report card while the sitting is still in review, marked "Not released". Only *release* waits for all approvals. The blueprint omits that in-review sheet. The spec already covers it.
4. **No staff report-card preview.** *(simplification)* Blueprint has no node for it. Spec: in review, staff can open the report card, marked "Not released" (see the "Report card preview" in the second flowchart and step 7). The blueprint omits that preview. The spec already covers it.
5. **Only the subject teacher enters marks.** *(simplification)* Blueprint: `Subject teacher: enter or upload marks`, `Note: subject teacher`. Spec step 2: the subject teacher, the class teacher, or the school admin, plus a Toshi mark, all through `ExamMarkWriter`. Phase 2 names the class teacher explicitly. The blueprint omits the other people who may enter marks. The spec already covers them.
6. **The admin is not the only place to assign a class teacher.** *(simplification)* Blueprint: `Note: assignment` says "This is the **only** place to assign", and `Note: school admin` says "only place to do it". Spec step 1, Decision 9 and phase 1: the admin dashboard is the screen, but the wizard, Toshi and the invite form call the same assignment service. The blueprint draws only that screen and its note leaves the other callers out. The spec already names them.
7. **Inviting a teacher has no invite step.** *(simplification)* Blueprint: `Admin: assign class teacher` collects `New teacher email`, and `Admin: record class teacher assignment` stores `invitedEmail`. Nothing sends or tracks an invite. Spec step 1 and phase 1: "invite a new one" is part of the one assignment service. The blueprint omits the invite itself. The spec already covers it.
8. **The log note covers less than the node.** *(simplification)* Blueprint: `Note: assignment` says "Replacing a current class teacher is logged", but `Admin: record class teacher assignment` logs every assignment. Spec Decision 9: pick, invite and replace each write a log entry. The node matches the spec. The note omits the other two log entries. The spec already covers them.
9. **Class-teacher release does not check "own class".** *(simplification)* Blueprint: `System: check who may release` lets `Releasing as = Class teacher` through whenever `classTeacherCanRelease` is on. It does not check that the person is P.4's class teacher. The role itself is a self-chosen dropdown on `Admin: release sitting`. Spec Decision 1 and step 6: a class teacher releases "their own class" only. Roles are authorised, not declared. The blueprint omits that ownership check. The spec already requires it, and the build must not copy the dropdown.
10. **WhatsApp recipients are not limited to the released class.** *(spec updated in this PR)* Blueprint: `System: record sitting released` sets `whatsappRecipients` to every approved parent with any linked student in the school. It ignores `whatsappOptIn` and does not filter to students in P.4 / this sitting. Spec phase 6, the release paragraph, Decision 3, step 6, and step 8 now state that a parent who has opted out of WhatsApp results gets none, and that a release only messages approved, linked parents of the students in the released class and sitting, never the whole school. The blueprint still messages the whole school and still ignores opt-out.
11. **The send is always a template.** *(simplification)* Blueprint: the template is the only push path. Spec ("Inbound MARKS, GRADES, and REPORT…" paragraph and step 8): the push uses a template when the 24-hour window is closed. Inside the window it can be a normal reply. The blueprint omits that window. The spec already covers it. A real-school send still waits until `results_released` is approved and the per-release switch is on (see 1 and 16).
12. **Only GRADES is answered on WhatsApp.** *(simplification)* Blueprint: `Parent: replies GRADES or taps See results, receives the marks`, `Note: GRADES reply`. Spec (second flowchart, step 8): inbound MARKS, GRADES and REPORT all stay behind `ReleaseGate`. REPORT also returns the report-card PDF through `StudentReportCardService`. The "See results" button is now in the spec and is handled exactly like GRADES (see 16). The blueprint still omits MARKS and REPORT. The spec already covers them.
13. **The family side only covers parents.** *(simplification)* Blueprint: `Parent: portal shows results`, `Parent: report card available`, `Note: portal` ("linked parents"). Spec ("The flow"): parents, students, alumni, Toshi, family report-card PDFs and WhatsApp all read through the gate. The second flowchart has "Parent and student portals". `Note: Toshi` mentions students, but no student or alumni portal node exists. The blueprint omits those readers. The spec already covers them.
14. **No lock or reopen after approval.** *(simplification)* Blueprint: once `Admin: approve subject` runs, nothing locks or reopens a subject, and nothing happens after release. Spec step 4 and phase 3: `MarksSubmissionService` owns lock, approve, reject (return) and reopen. The blueprint omits lock and reopen. The spec already covers them.
15. **An uploaded file has no parse or preview step, and it is not matched by registration number.** *(simplification)* Blueprint: `Subject teacher: save marks as draft` only labels `markSource` "Uploaded file (to be parsed)", and the marks it saves come from the typed fields, which are all blank when a file is uploaded. Spec step 2 and "Rules that already hold": `MarksImportService` parses and previews, then calls `ExamMarkWriter`. The import matches the registration number, not the display name. The blueprint omits that parse. The spec already covers it.
16. **The results template wording and button were missing from the spec on `main`.** *(spec updated in this PR)* Blueprint: `Note: WhatsApp template` names `results_released`, gives its body ("Hello {{1}}, {{2}} has released the {{4}} results for {{3}}. Tap See results or reply GRADES to view them here.") with variables 1 parent, 2 school, 3 student, 4 sitting, and the "See results" quick reply. On `main` at `ac36ca66` the spec called that template missing, with no name and no button, and listed the variables in a different order. This pull request records `results_released`, UTILITY, English, submitted to Meta and pending approval, with that body and with "See results" handled exactly like GRADES. No real school gets the send until it is approved and the admin's per-release switch is on. The blueprint already matched the submitted template.
17. **Nursery wording.** *(simplification)* Blueprint: `Note: not in this version` lists "Nursery ratings" as out of scope. Spec Decision 7 and step 2: nursery ratings stay on the existing ratings form, unchanged. The blueprint leaves that form out of this picture. The spec already says the form stays, so the wording does not change the spec.

## Agreements worth noting

Saving, submitting, approving and releasing are separate states (Draft → Submitted → Returned/Approved → Released). Approval is required with no override. By default only the admin releases, and the class-teacher setting is off by default. Submitting does not notify parents. The return reason is visible only to the owning teacher and school admins, and it shows on the entry page. The entry form shows saved marks. The sheet covers one sitting for the whole class, with a stream column and filter, and blanks are never zero. Nothing reaches a family before release. Google Sheets, a whole-term sheet and a release override are out of this version. Each query is scoped to one school.
